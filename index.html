Learning what vs. learning howDecomposing task and interface competence in agentic training

A model may have the knowledge and reasoning to solve a task yet fail to express it through a particular harness. We distinguish task competence from interface competence, show how training on one harness can interfere with another, and introduce harness rehearsal: training on traces that carry minimal task knowledge while exercising the target interface.

The idea

A two-component view of agentic competence

An agent acts through a harness, an interface that determines what it can observe, which actions it can take, and how those actions are interpreted. A coding agent may identify the correct fix but mishandle the shell. A clinical agent may reason correctly about a patient record but fail to retrieve or submit the required information.

Observed performance under a harness therefore reflects both the quality of reasoning about the task and the ability to carry out the intended actions through the harness. We distinguish task competence, the knowledge and reasoning needed to solve a task, from interface competence, the ability to carry out a solution through a particular harness, and ask whether they can be learned, transferred and lost independently.

Task competence

Learning what

The knowledge and reasoning needed to solve a task. Our hypothesis: it can transfer across harnesses.

Interface competence

Learning how

The ability to act on that knowledge through a given harness. Our hypothesis: it is more sensitive to interference than task competence.

Q1

Harness choice exposes different capabilities of a policy

Performance varies substantially across harnesses. On MedAgentBench, Qwen3-4B's mean success ranges from about 4% to 36%. The differences are not merely in overall strength: on every benchmark, weaker-performing harnesses solve tasks that the best-performing harness does not, accounting for 17% of all solved tasks on MAB, 11% on BFCL-MT and 5% on RG.

Q2

Distillation couples task and interface learning

Each distillation trace jointly supervises the task solution and its execution through a particular harness. We evaluate single-harness specialists and 3H, trained on all three training harnesses, on every training harness and on a fourth, held-out harness.

Single-harness distillation improves the training harness but can reduce performance on other harnesses, sometimes well below the base policy: fc distillation takes json from 33.5 to 0.1. This suggests that specialising to one harness can interfere with competence on others. Training on three harnesses tends to mitigate this collapse on the held-out harness, but does not consistently move it beyond the base policy: it rises on MAB and AppWorld, stays near base on BFCL and falls on RG. This leaves open whether the held-out gap reflects missing task knowledge or missing interface competence, which we probe next with harness rehearsal.

Q3

Harness rehearsal:disentangling task and interface supervision

Harness rehearsal provides supervision on the target interface while minimising supervision on how to solve the underlying task. For each training task with a known solution, we write an instruction ρ(x) that specifies the operations needed to obtain and submit it. The environment and verifier are unchanged, so the model only has to execute the prescribed operations correctly through the target harness. Runs that pass the original verifier become rehearsal traces.

Task and interface supervision interact

Neither cross-harness task demonstrations nor rehearsal alone substantially outperforms the base policy, but combining task and interface supervision yields much larger gains on the target harness. Task supervision from other harnesses becomes substantially more effective once the model (re)learns to operate the target interface.

The interaction does not rely on task content in the rehearsal traces. On Reasoning Gym, rehearsal consists only of transcribing a provided answer, and the rehearsal traces provide no task knowledge that can transfer to evaluation. Rehearsal and cross-harness supervision reach 20.0 and 19.8 on their own, but 37.0 when combined.

Q3 · failure analysis

How does harness rehearsal change failure modes?

To see how rehearsal changes failure modes, we labelled every failed trial on the target harness by its first decisive error: a task-knowledge failure (well-formed actions, incorrect content), or one of three interface failures: invalid calls (the harness could not parse or execute the action), incorrect submissions (the answer was not delivered as the harness expects) and termination failures (the run did not end properly). Automatic rules, deterministic but imperfect, label all 2,347 failed trials, so three annotators, blind to the checkpoint, also labelled 100 sampled failures.

Rehearsal reduces interface failures on all three benchmarks. On BFCL-MT and RG, interface failures fall by more than the total gain in success, so runs that previously failed at the harness now proceed far enough to fail on task content instead. On MAB, failures drop from 223 to 158 of 244 trials, and 19.1 of the 26.6-point gain comes from fewer interface failures. The remaining interface errors shift from incorrect submissions to invalid calls.

Rehearsal also reproduces the cross-harness interference induced by specialist training. On BFCL-MT, rehearsing only on fc collapses performance on the remaining harnesses: json drops from 33.5 to 0.0 and pycall from 28.2 to 0.1, mirroring the fc specialist (0.4 on json, 19.5 on pycall). This suggests that the interference reflects interface competence rather than loss of task knowledge.

Q4

Multi-harness competence persists through subsequent RL

We run GRPO through one harness or all three, with matched rollout counts, and ask whether single-harness RL shows the same interference as single-harness SFT. It does not. Single-harness SFT can push other harnesses below the base model, whereas single-harness GRPO through the same harness leaves them at or above base.

Multi-harness competence learned during distillation also carries through RL. Starting from the 3H-SFT checkpoint, single-harness GRPO preserves performance on the other harnesses, including the held-out one. On MAB, fc rises from 56.4 after 3H SFT to 61.4 with parity rollouts and to 66.9 with Terminus-2 rollouts, and multi-harness GRPO gives the best results on parity, fc and held-out xml.

Insights

Task competence transfers, but interface competence decides whether it shows

  1. Task supervision collected through other harnesses becomes substantially more useful on a target harness once the model has learned how to operate it: 8.5 → 58.8 on BFCL-MT, 2.0 → 34.4 on MAB, 19.8 → 37.0 on RG.

  2. A single-harness specialist can impair performance on another harness from 33.5 to 0.1 (BFCL-MT). Multi-harness distillation tends to mitigate this collapse.

  3. Interface competence is more sensitive to interference, but it can often be acquired independently, at substantially lower cost than retraining on the full task set through the target harness.

  4. Interface competence learned during distillation persists through GRPO, where single-harness training does not substantially degrade performance on the other harnesses.

Looking ahead

Open questions

  1. Why is on-policy RL more robust to single-harness training? Single-harness GRPO does not show the same degree of cross-harness interference as single-harness SFT, whether it starts from the base model or from 3H SFT. Understanding what protects interface competence during on-policy training would tell us when single-harness RL is enough.

  2. How far does interface competence travel? We evaluate one held-out harness per benchmark. Relating transfer to how similar a held-out harness is to the training harnesses, for example through an explicit measure of harness distance, could help predict when cross-harness supervision transfers and how much target-interface practice is needed.

  3. How do other model families respond? We focus on Qwen3-4B, with additional results on Gemma-3-4B-it. The main training-harness patterns are similar across both models, while held-out transfer varies more, which suggests that sensitivity to interface training may differ across model families. Studying a wider range of models would help characterise this.

  4. What about harnesses that expose different tools? We focus on tasks that can be executed across multiple harnesses without relying on specific tool availability, external memory or skills. This helps isolate the general effect of different harnesses. Extending the analysis to settings where harnesses differ in the tools or auxiliary capabilities they expose would help disentangle interface competence from competence that depends on access to additional resources.
